# MemHarmony 真机对比实验计划

## Summary

目标是在同一台 HarmonyOS NEXT 真机上证明三件事：

1. 语义记忆检索比关键词搜索更有效。
2. 在 Recall 不下降的前提下，Graph-Aware 缓存、异步 I/O 和预取能降低尾延迟或磁盘读取。
3. 引擎在受限内存、动态读写和进程重启条件下仍然可靠。

默认使用单台真机；SIFT100K 为必做性能集，SIFT1M 在约 2 GB 索引可导入应用沙箱时追加。所有正式结果运行 5 轮并报告中位数。

## 实验准备

- 固定真机型号、系统版本、HAP、模型、索引和编译选项。
- 使用 Release 构建，关闭调试日志；查询和 I/O 均不得运行在 UI 线程。
- 性能实验前关闭省电模式和无关应用，开启飞行模式，亮度固定，设备不充电。
- 每轮开始要求温度状态为 `NORMAL`，电量保持在 30%–90%，两轮间等待温度恢复。
- SIFT100K 取前 100,000 条 base，必须重新计算对应精确 ground truth，不能使用原 SIFT1M truth。
- 固定 200 条 SIFT 查询、100 条中文语义查询；数据、查询、标签和索引全部版本化。
- “冷缓存”定义为重启 Native 引擎并清空用户态 BufferPool；普通 HAP 无权清除系统 Page Cache，因此报告中不得称为“物理磁盘完全冷启动”。
- 每轮查询顺序由固定种子打乱，五轮种子为 `42,43,44,45,46`；各方案采用轮换顺序，抵消温度和系统状态影响。

## Benchmark 接口

扩展 `BenchmarkConfig`，加入：

- `benchmarkMode`: `VECTOR_ONLY | END_TO_END | MIXED_RW`
- `engineVariant`: `SYNC_LRU | SYNC_GRAPH_2Q | ASYNC_GRAPH_2Q | FULL_ENGINE`
- `cacheCondition`: `PROCESS_COLD | STEADY_STATE`
- `seed`、`queryOffset`、`durationSec`
- `readThreads`、`writeThreads`、`readRatio`、`writeRatio`

`BenchmarkReport` 必须记录：

- 请求配置和实际生效的 I/O、缓存、预取配置
- 每轮及每查询原始延迟
- Recall、QPS、P50/P95/P99
- demand reads/query、cache hit rate、prefetch useful/waste rate
- 初始化前 RSS、峰值 RSS、Native 预算内存
- 起止电量、温度状态、错误和 fallback 原因
- CRUD 数量、恢复时间、写入确认序列号

若实际 I/O 模式发生 fallback，该轮标记无效，不得归入目标方案。

## 对比矩阵

### 1. 语义检索价值

使用 5,000 条校园知识和 100 条人工标注查询。

| 方案 | 检索方式 |
|---|---|
| Keyword | RDB 关键词 OR 匹配，关键词在实验前固定 |
| MemHarmony | bge 端侧嵌入 + Native 向量检索 |

记录 Top-1、Top-3、MRR@10、端到端 P95。通过标准：

- MemHarmony Top-3 命中率 `>=80%`
- 相比 Keyword 提升 `>=15` 个百分点
- 端到端 P95 `<800 ms`

### 2. 核心系统消融

使用 SIFT100K、TopK=10、并发度 1，PROCESS_COLD 和 STEADY_STATE 各跑 5 轮。

| 方案 | I/O | 缓存 | 预取 |
|---|---|---|---|
| A 同步基线 | `pread` | LRU，20%预算 | 关闭 |
| B 图缓存 | `pread` | Graph-Aware 2Q，20% | 关闭 |
| C 异步路径 | thread-pool pread | Graph-Aware 2Q，20% | 关闭 |
| D 完整引擎 | thread-pool pread | Graph-Aware 2Q，20% | PQ预取 |

统一使用相同 PQ、Vamana 索引、search width、beam width、rerankTopK 和查询序列。

判定规则：

- 所有方案 Recall@10 `>=0.95`
- 相对 Recall 下降不得超过 `0.001`
- D 相对 A：P95 降低 `>=15%` 或 QPS 提升 `>=20%`
- B 相对 A：demand reads/query 降低 `>=20%` 或 P95 降低 `>=10%`
- D 相对 C：P95 降低 `>=5%`、P99 降低 `>=8%`，且预取浪费率 `<=30%`

预取未通过最后一项时，不将预取作为主要性能创新。

### 3. 并发能力

只比较 A 与 D，STEADY_STATE 下测试并发度 `1/4/8`，每组运行 60 秒、3 轮。

记录 QPS、P95/P99、I/O 队列深度和错误数。要求 D 在并发增加时无崩溃、无死锁，且并发 4 时相对 A 保持性能优势。

### 4. 资源自适应

使用完整引擎分别运行：

| 档位 | 缓存预算 | I/O 深度 | 预取 |
|---|---:|---:|---|
| NORMAL | 20% | 8 | 4页 |
| CONSTRAINED | 10% | 4 | 2页 |
| CRITICAL | 4% | 1 | 关闭 |

每档 200 条查询、5 轮。要求配置实际生效、Recall 下降不超过 `0.001`；CRITICAL 下零 OOM、零 Native 崩溃。报告进程峰值 RSS和相对性能退化，不把 Native 内存估算冒充真实 RSS。

### 5. 混合读写与恢复

比较 A 与 D，共用同一套 WAL/MemTable/SSTable 动态层：

- 纯读 `100/0`
- 常见负载 `95/5`
- 高写负载 `80/20`
- 4 个 reader、1 个 writer，每场景 60 秒、3 轮
- 主吞吐实验关闭精确 Recall 回算
- 另跑限速 Recall 抽样验证 base/delta merge

随后执行 100 次固定 CRUD 和 10 次写入阶段强杀进程。要求：

- 零已确认记录丢失
- 删除记录不复活
- 重复恢复保持幂等
- 连续 500 次查询零 Native 崩溃
- 单独报告恢复时间、写入P95和Compaction期间查询P99

生成一份汇总 JSON、CSV、测试报告和四张核心图：

1. Keyword 与 MemHarmony 的 Top-3 命中率。
2. 四种系统方案的 P95/P99。
3. Recall–P95–内存三维 Pareto 图。
4. NORMAL/CONSTRAINED/CRITICAL 的 RSS 与延迟。

最终仅在全部护栏通过后使用以下结论：

“在 Recall@10 不低于 0.95 的条件下，MemHarmony 相比鸿蒙同步 LRU 基线将真机查询 P95 降低 X%，demand reads/query 降低 Y%，并在 4% 缓存档位和持续动态写入条件下保持正确检索与崩溃恢复。”

## Assumptions

- 使用单台 HarmonyOS NEXT/API 12+ ARM64 真机。
- SIFT100K 是必须完成的正式规模；SIFT1M 是部署条件允许时的增强实验。
- 索引在主机离线构建，真机只加载和查询，不在真机实时建大图。
- 能耗仅在 DevEco Profiler或可靠系统接口可测时报告；否则只记录电量和温度，不给出虚构的 mAh 结论。
